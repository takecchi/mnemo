# ADR 0008: 「無い」を分類して返す

- **状態**: 採用 (2026-09)

- **文脈**:
  recall が候補を返さなかったとき、それが「探して無かった」のか「そもそも探していない」のか、
  「候補には出たが基準に届かなかった」のかを区別できないと、呼び出し側は「0件だった」という
  1ビットの情報しか得られない。mnemora が掲げる原則（`docs/vision.md` の Qualified Presentation の
  第3の現れ「結果は、そこから漏れたものと必ず同時に提示する」）を型として実装する必要がある。

- **決定**:
  `RecallResult.omitted` に、返らなかったものを表す `Omission[]` を持たせる。`Omission.kind` は
  少なくとも次を区別する（「0件」に潰さない）:
  - `stage_skipped` — その段を実行していない（埋め込み provider 不達・クエリに埋め込む内容が無い・
    予算切れ、など理由付きで）
  - `filtered` — 条件で落ちた（tenant / status / archived / taxonomy / 期間、どの条件かを添えて）
  - `below_threshold` — 候補に出たがスコアが閾値未満（惜しかった上位数件とそのスコアを添えて）
  - `over_limit` — 閾値は超えたが `k` に入らなかった
  - `budget_dropped` — `k` には入ったが文字数/トークン予算で落とした
  - `not_indexed` — Memory としては存在するがまだ埋め込みが無い
    （`docs/decisions/0003-memorystore-vs-vectorstore.md` の `embeddingStatus`）
  - `ann_truncated` — ANN の候補打ち切りで見えていない可能性がある領域
    （`docs/decisions/0004-decay-at-query-time.md` の over-fetch の限界）

  **さらに、件数そのものにも「無いの種類」を適用する。**`Omission.countKind: 'exact' | 'lower_bound' | 'unknown'`。
  フィルタで落ちた件数は SQL で正確に数えられるが、ANN が返さなかったものの件数は原理的に数えられない
  ——推定値を実測値の顔で出さない。

  **`recallId` を発行して recall を記録する。**`recalls` テーブルに1回の recall 操作を記録し、
  戻り値の `recallId` を呼び出し側が持ち帰る。

- **検討した選択肢**:
  - **自然文の説明文字列を1本返す**（例:「該当する記憶は見つかりませんでした」）: 実装は最も単純だが、
    呼び出し側がプログラムでこの文字列を解釈して次の一手を変えることができない。文言変更が
    呼び出し側のロジックを壊すリスクもある。却下。
  - **ログにだけ出す**（`omitted` の詳細を構造化ログに書き、`RecallResult` には含めない）:
    デバッグ・監視には使えるが、**呼び出し側（recall を呼んだアプリケーション）が実行時に
    次の一手を変えられない。**「埋め込みがまだ無いので後で再検索すべきか」「予算を広げれば
    もっと出るのか」といった判断を、recall の戻り値だけで完結させられなくなる。却下。
  - **`Omission.kind` を持つ判別可能ユニオンとして戻り値に含める**: 採用。

- **理由**:
  1. 呼び出し側が「なぜ無いのか」に応じて異なる振る舞いを取れる必要がある（例: `not_indexed` が
     多ければ埋め込みパイプラインの遅延を疑う、`budget_dropped` が多ければ予算設定を見直す）。
     これは構造化されたデータでなければプログラムから使えない。
  2. 件数の正確性（`countKind`）を分けることで、「正確に0件」と「少なくともこれだけはある
     （下限のみ分かる）」と「見積もれない」を区別できる。これを1つの数値に潰すと、呼び出し側は
     常に「正確な0件」だと誤解しうる。
  3. `recallId` を発行して記録することで、`observe({kind: 'memory_usage', recallId, usedMemoryIds})`
     が「どの recall のどの候補が実際に使われたか」を後から結びつけられる。

- **⚠ 正直に書くこと（alteroid との関係）**:
  この原則自体は採用するが、**alteroid (github.com/takecchi/alteroid) で実証されたものではない。**
  現物を確認したところ、alteroid には**スコア付き検索が存在しない。**記憶へのアクセスは
  `memory_list`（一覧）と `memory_read`（slug 指定で開く）のみであり、埋め込み・ベクトル検索・
  rerank に該当する処理はリポジトリ全体で1件もヒットしない。確認できたのは、日誌の部分一致検索
  （`ILIKE` によるキーワード一致）が0件だったときに、「探索対象に入っていない欄がある」ことまで
  自然文で応答に含めている、という1例のみである。
  **核となる発想（「0件」と「そもそも探していない」を区別する）は alteroid のこの1例で確認できた。
  だがそれは自然文の1メッセージであり、型として構造化されたものではない。**
  `Omission.kind` のような判別可能ユニオンに持ち上げるのは、alteroid の延長ではなく、**mnemora で
  新しく行う設計**である。この違いを docs で潰さない（詳細な調査記録は
  [docs/alteroid-findings.md](../alteroid-findings.md) 主張Bを参照）。

- **結果（この決定が招くもの）**:
  良い面: 呼び出し側が「0件」の内訳をプログラムで解釈でき、抑止すべき原因（埋め込み遅延、予算不足、
  閾値の厳しさ）を切り分けられる。`recallId` の発行により、explainability（説明可能性）と
  reinforcement（強化）が同一の記録機構を共有できる（下記）。

  引き受ける負債:
  - パイプラインの各段が「なぜ落としたか」という理由を持ち回る必要があり、実装が重くなる。
    段を追加・変更するたびに、その段がどの `Omission.kind` を生成しうるかを設計する手間が増える。
  - 件数の厳密性（`countKind: 'exact'`）を保証したい場面では、追加のクエリ（`count(*)`）が
    必要になることがある。近似で済ませられる場面と厳密さが必要な場面を呼び出し側が選べるように
    する必要があり、これは recall のオプションとして別途設計する。
  - API の戻り値（`RecallResult`）が大きくなる。単純な「上位k件を返すだけ」のクライアントには
    冗長に見える可能性がある。

- **これが覆るとしたら**:
  - `omitted` の情報量が実際には使われず(呼び出し側が `memories` だけを見て `omitted` を無視する
    実装ばかりになる)、API の複雑さに見合わないと分かったら、`omitted` を既定で省略可能なオプション
    フィールドに格下げすることを検討する。
  - `countKind` の3値では実運用の要求に足りない（例えば「推定の信頼区間が欲しい」）と分かったら、
    型を拡張する。

- **確かめていないこと**:
  - `Omission.kind` の7種で実際の失敗・除外パターンを網羅できているかは、Phase 1 の実装・運用を
    経ないと分からない。列挙は現時点で想定できる理由に基づくものであり、閉じた集合として
    設計してはいない。
