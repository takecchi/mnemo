# ADR 0003: MemoryStore と VectorStore を分けるか

- **状態**: 採用 (2026-09)

- **文脈**:
  Memory の永続化（本体・status・provenance など）とベクトル検索用の索引（埋め込み）を、同じ interface に
  乗せるか分けるか。埋め込みモデルは複数持てるべきであり（多言語対応、モデル移行）、埋め込みの完了は
  Memory の作成と同時には起きない（同期/非同期のどちらの抽出経路でも、埋め込みは Memory の後から付く）。
  この非同期性を interface の形でどう扱うかが問題になる。

- **検討した選択肢**:
  - **1つの `Store` にまとめる**: Memory 本体と埋め込みを同じ interface・同じ操作単位で扱う案。
    実装は単純になるが、埋め込み空間は複数持てるべきという要求（`0002-embedding-space-tables.md`）と
    整合しない。Memory の寿命と埋め込みの寿命が一致しない（Memory は変わらないままモデルだけを
    入れ替えたい場面がある）ため、一体化すると「埋め込みモデルを変える」という操作が実質的に
    「Memory を作り直す」という操作に化ける。却下。
  - **interface としても実装としても完全に分離し、常に別システムに置く**: 差し替え可能性は最大化するが、
    Phase 1 で分散システムの整合性問題（2フェーズコミット、あるいはそれに準ずる調整）を持ち込むことになる。
    mnemo の規模と Phase 1 の要求に対して過剰。却下。
  - **interface は分けるが、リファレンス実装では同一 DB・同一トランザクションに置く**: 採用（下記）。

- **決定**:
  **interface としては `MemoryStore` と `VectorStore` を分ける。ただし `packages/postgres` という
  リファレンス実装では同一 DB・同一トランザクションで両方を実装する。**
  分離は「差し替えのため」であり「分散のため」ではない。Phase 1 で2フェーズコミットのような
  分散トランザクション機構を持ち込まない。

- **理由**:
  1. **`MemoryStore` は真実の源(source of truth)であり、`VectorStore` は再構築可能な派生索引である。**
     この非対称性そのものが契約になる。`VectorStore` を失っても `MemoryStore` から再 embed すれば
     復旧できるが、逆はできない。adapter はこの非対称性を守らなければならず、「VectorStore の内容だけを
     唯一の正とする」実装を許さない。
  2. 埋め込み空間は複数持てるべきで（再 embed 移行・多言語）、Memory の寿命と埋め込みの寿命が一致しない。
     interface を分けておけば、将来 `VectorStore` だけを別システム（専用ベクトル DB 等）に差し替える
     余地を残せる。一体化した interface ではこの差し替えが型のレベルで不可能になる。
  3. 分離してもなお Phase 1 では同一 DB・同一トランザクションに実装を寄せることで、分散システムの
     整合性問題を先送りできる。「型としての柔軟性」と「運用の単純さ」を両立できる。

- **結果（この決定が招くもの）**:
  良い面: 埋め込みモデルの移行やベクトル DB への将来的な差し替えが interface の変更なしに行える。
  `MemoryStore` の正しさとベクトル索引の正しさを別々に検証できる（`packages/testkit` で個別の
  適合テストを書ける）。

  引き受ける負債・制約:
  - **別システムに置いた場合の不整合を、隠さずに型で表す必要がある。** `Memory` に
    `embeddingStatus: 'pending' | 'ready' | 'failed' | 'skipped'` を持たせる。これにより recall は
    「Memory としては存在するが、まだ埋め込みが無く候補にすら上がらなかった」件数を
    `omitted.kind = 'not_indexed'` として報告できる（`docs/decisions/0008-absence-taxonomy.md` と直結）。
    索引の遅れを黙って無かったことにしない、という設計上の負債の引き受け方である。
  - リファレンス実装が同一トランザクションであるという事実に開発者が慣れると、「常に整合している」という
    誤った前提でコードを書きがちになる。ドキュメントと testkit の両方で、`VectorStore` は別システムに
    置かれうるという前提を明示し続ける必要がある。

- **これが覆るとしたら**:
  - Phase 1 以降、実際に `VectorStore` を別システム（専用ベクトル DB 等）に置く要求が具体化したら、
    `embeddingStatus` の遷移（`pending → ready/failed`）をどう駆動するか（outbox 経由の非同期更新か、
    同期呼び出しの二段書き込みか）を別途 ADR として起こす必要がある。本 ADR はその設計を先取りしていない。
  - 同一 DB・同一トランザクションの実装で性能上の問題（ベクトル索引の書き込みが Memory 本体の
    トランザクションを長時間ブロックする等）が実測されたら、書き込み経路の非同期化を再検討する。

- **確かめていないこと**:
  - `embeddingStatus` が `pending` のまま放置される時間の運用上の上限（監視・アラートの閾値）は
    未検討。Phase 1 のスキーマには列を持つが、運用ルールは今後の課題として残る。
