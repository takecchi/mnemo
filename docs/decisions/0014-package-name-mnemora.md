# ADR 0014: 名前を `mnemora` / `@mnemora/*` に確定する

- **状態**: 採用 (2026-09)

- **文脈**:
  名前は設計フェーズの当初から**仮**のままだった。`docs/vision.md` の「名前について」は
  「unscoped の `mnemo` は npm に既に存在する（2014年公開・Rufus::Mnemo の JS 移植・
  最終更新 2022-06）」「`@mnemo/core` は 404（未公開）」までは確認できたが、
  **`npm` の org `mnemo` が確保できるかどうかは確かめられなかった**（org のページが
  未ログインだと 403 を返すため）と明記していた。そのうえで
  「`@mnemo/*` の維持を推すが、最終判断はオーナーに委ねる」で止まっていた。

  この未決は `docs/roadmap.md` §5「設計上まだ判断が必要な点」の **§5.1「npm org `mnemo`
  が取れなかった場合の名前」**として、**オーナーの判断を待つ6項目のひとつ**に載っていた。
  §5 の項目は「妥当なデフォルトを技術側だけで決め切れない」ものだけを置く場であり、
  ここに載っている以上、技術側が勝手に決めてよい事項ではなかった。

  2026-09-05、オーナーがこの項目に判断を下した。本 ADR はその決定と、決定が招いた
  変更（コード・文書・DB の台帳テーブル名）を記録する。

  **なお、publish 前である。** npm にはまだ何も公開していないため、名前を変える
  コストがいちばん安い窓がいまである、という事情も判断の前提にある。

- **検討した選択肢**:
  - **`@mnemo/*` の維持**（`docs/vision.md` の当時の推し、`docs/roadmap.md` §5.1 の第一推奨）:
    scope 付きなら unscoped の `mnemo` と実務上衝突しない、既存の `mnemo` は更新の
    止まった別ジャンルの小パッケージなので検索上の混同リスクは低い、というのが当時の
    理由だった。**採らなかった理由はオーナーの判断であり、この ADR の書き手には
    現物から読み取れない。**推測で埋めない。読み取れるのは「org `mnemo` を取れるか
    確かめられていなかった」という当時の未確認事項が残っていたことだけである。
  - **`@mneme/*`**（roadmap §5.1 の代案の第一候補）: ギリシャ神話の記憶の女神で意味が
    近く、unscoped の `mneme` は存在するが scope が別なので衝突しない、という評価だった。
    **採らなかった理由はオーナーの判断である。**
  - **`@anamnesis/*`**（同）: 「想起」そのものを指す語で意味は強いが、当時の評価として
    「読みにくく打ちにくい」とされていた。**最終的に採らなかった理由はオーナーの判断である。**
  - **`@recall-os/*`**（同）: 機能語なので衝突しにくいが、当時の評価として
    「名前としては凡庸」とされていた。**最終的に採らなかった理由はオーナーの判断である。**
  - **`@mnemora/*`（採用）**: **上の候補一覧のどれでもない。**roadmap §5.1 が挙げた
    候補の外から、オーナーの判断で選ばれた名前である。「推奨どおりに決まった」のでは
    ないことを、ここで明示しておく。

- **決定**:
  **プロジェクト名を `mnemora`、npm のスコープを `@mnemora/*` に確定する。**
  仮ではない。以後、新しい記述で `mnemo` / `@mnemo/*` を使わない。

  - パッケージ名: `@mnemora/core` / `@mnemora/postgres` / `@mnemora/testkit` /
    `@mnemora/openai` / `@mnemora/example-chat`、リポジトリのルートは `mnemora`。
  - **npm の org `@mnemora` は、オーナーが自分で作成し、使用できることを確認した。**
    **この確認をしたのはオーナーであり、このリポジトリの作業者ではない。**本 ADR は
    npm の状態を自分では確かめていない（「確かめていないこと」を参照）。
  - `docs/roadmap.md` §5.1 はこの決定により解決済みとする。項目自体は
    「以下の6項目に限る」という §5 冒頭の記述を保つため、§5.2 と同じく残したまま
    追記で閉じる。

- **理由**:
  1. **確定させる判断そのものが、オーナーの領分だった。**§5.1 は「外部サービスの
     空き状況に依存し、ブランディングと将来の公開範囲に関わる」ためオーナー判断とされた
     項目である。技術側にはこれを決める根拠が無く、決まらない限り文書は
     「名前は仮である」と書き続けるしかなかった。
  2. **`@mnemora` はオーナーが実際に org を作成し、使用できることを確認できている。**
     `@mnemo` について残っていた未確認事項（org を確保できるか）は、この名前では
     解消している。§5.1 が立てていた「取れなかった場合どうするか」という問い自体が消えた。
  3. **publish 前のいまが、改名のコストがいちばん安い。**公開後の改名は利用者の
     `package.json` を割る。まだ誰も依存していないうちに終わらせるほうが安い。

- **結果（この決定が招くもの）**:

  **コード・設定**（別コミット `c83c32e`）: パッケージ名・スコープ・`bin`
  （`mnemo-postgres-migrate` → `mnemora-postgres-migrate`）・tsconfig の `paths`・
  vitest の alias・CI のデータベース名（`mnemo_ci` → `mnemora_ci`）を新しい名前へ移した。
  `examples/chat/src/mnemo-path.ts` とそのテスト2本は `mnemora-path.*` へ改名し、
  `runMnemoPath` / `buildMnemoPrompt` / `MnemoPathOptions` / `MnemoPathResult` と
  `compare` の `mnemoChars` / `mnemoTokens` / `mnemoShareOfNaiveChars` も `Mnemora` 系にした。

  **文書**: `README.md` / `AGENTS.md` / `docs/**` の製品名を `mnemora` に追随させた。

  - **ADR 0001〜0013 の本文に出る製品名は `mnemo` から `mnemora` へ更新したが、
    決定の内容・理由・結論は一切変えていない。**これらの ADR には `@mnemo/*` 形式の
    パッケージ参照は1件も無く、すべて「mnemora は Postgres を必須としている」型の
    現在形の製品記述だったため、呼称だけを差し替えれば足りた。
  - **当時の名前としての記録は `docs/vision.md`「名前について」の経緯節に保全してある。**
    他人の npm パッケージ `mnemo`（Rufus::Mnemo の JS 移植）への言及、当時の推奨
    （`@mnemo/*` の維持）、当時の未確認事項（org `mnemo` の取得可否）は、**1文字も
    書き換えずにそのまま残した。**書き換えると事実が嘘になるためである。
    同じ理由で `docs/roadmap.md` §5.1・§6 と `docs/memory-model.md` の
    「確かめていないこと」に残る `mnemo` も原文のまま残し、追記だけを添えた。

  **DB（マイグレーション適用済み台帳）**: 適用済みマイグレーションを記録するテーブル名を
  **`_mnemo_migrations` → `_mnemora_migrations`** に改名し、`packages/postgres` の
  `migrate` に**旧名が在れば引き継ぐ冪等な処理**を入れた
  （`handOverLegacyMigrationsTable`。`to_regclass` で新旧の有無を見て、
  「旧名が在り新名が無い」ときだけ `ALTER TABLE ... RENAME TO` する。旧名が無ければ
  何もせず、新旧どちらも在れば何もしない——新名を上書きせず、旧名も勝手に消さない）。
  台帳を読む前に必ず一度通す。

  歯は `packages/postgres/src/__tests__/migrate-ledger-handover.test.ts`（別コミット
  `24e281c`）。**まっさらな DB で migrate が通ることは引き継ぎを何も測っていない**ため、
  旧名の台帳と適用済みの行を先に作ってから測る。作り直しでは復元されない番兵の行を
  1行混ぜて、「引き継がれた」と「作り直された」を区別している。

  この形を採った理由は、**「既存の DB は無い」は誰にも確かめられない**からである。
  publish 前だから利用者の DB は無いはずだ、という推定は、開発者や CI が既に作った
  DB を勘定に入れられない。引き継がずに新名の台帳を作ると**空の台帳を読むことになり、
  `migrations/*.sql` を最初からやり直そうとして落ちる**（`0001_init.sql` の
  `CREATE TABLE observations` は `IF NOT EXISTS` を付けていない）。
  publish 前のいまがいちばん安い窓であることは事実だが、**その安さを「既存の DB は無い」
  という確かめられない前提の上に置かず、前提に依存しない形にした。**

  **引き受ける負債**:
  - 「新旧どちらの台帳も在る」DB は、この処理では収束しない（何もしない）。中身の
    突き合わせは人間の判断に属すると考え、自動では触らないことにした。この状態に
    落ちた DB があれば、手で解決する必要がある。
  - 検索・リンクの外部からの流入（もしあれば）は旧名を指したままになる。publish 前で
    あるため実害は無いと見ているが、**外部からの参照が実際に存在しないことは
    確かめていない。**

- **これが覆るとしたら**:
  - npm の `@mnemora` org が、なんらかの理由で publish 時点で使えなくなっていた場合。
    その時点で名前をもう一度選び直すことになる（本 ADR は org が使えることの確認を
    オーナーの報告に依拠しており、自分では確かめていない）。
  - unscoped の `mnemora` を将来 publish したくなり、それが既に他者に使われていた場合。
    scope 付きの `@mnemora/*` の判断自体は覆らないが、「unscoped も押さえる」という
    前提で何かを組むことはできなくなる。
  - 商標・ブランドの観点から名前を変える必要が生じた場合。これは技術側の判断ではなく、
    §5.1 と同じくオーナーの領分に戻る。

- **確かめていないこと**:
  - **npm 上の `mnemora` / `@mnemora` の状態を、私たちは確認していない。**org `@mnemora`
    を作成し使用できることを確認したのは**オーナー**であり、このリポジトリの作業者は
    npm に問い合わせていない。本 ADR が書けるのは「オーナーが確認した」ところまでである。
  - **unscoped の `mnemora` については何も調べていない。**既存パッケージの有無・
    名前の近い既存パッケージとの混同可能性のいずれも未調査である。
  - 商標・他言語での語感・検索上の衝突は調べていない。
  - `_mnemo_migrations` から `_mnemora_migrations` への引き継ぎを、**この文書を書いた側は
    実 DB に対して観測していない**（文書を書いた環境に Postgres が無く、`packages/postgres`
    の DB 依存テストは `DATABASE_URL` が無いと走らない）。歯は在るが、それが緑になるのを
    見たのはこの文書の書き手ではなく、CI と実装者である。
