# ADR 0015: ルートの `test` 門は、DB テストを「走らせなかった」と明示する

- **状態**: 採用 (2026-09)

- **文脈**:

  `packages/postgres` と `examples/chat` の検査は本物の Postgres + pgvector を要求し、
  `DATABASE_URL` が無ければ即エラーになる（`test-db.ts` の `requireDatabaseUrl`。
  擬似物へ黙ってフォールバックしない、という `AGENTS.md` の方針）。
  そのため**両パッケージのスクリプト名は `test` ではなく `test:db` に分けてあり**、
  ルートの `pnpm -r --if-present run test` の対象から外れていた。

  これは意図的な設計である。PR #3 の本文に理由がそのまま残っている:

  > `packages/postgres` は `test` スクリプトを持たない（`test:db` のみ）ため、
  > DB 無しでも `pnpm run test` は自動的にスキップされる。

  **その意図（DB を持たない環境でルートの門を通す）は正しい。** 壊れていたのは別のところで、
  この設計は同時に**三つの状態のうち二つを、区別の付かない同じ緑に潰していた**:

  | 状態                            | 当時のルート門                     |
  | ------------------------------- | ---------------------------------- |
  | DB テストが通った               | 緑                                 |
  | **DB テストが落ちた**           | **緑**（手元では何も出ない）       |
  | **DB が無いので走らせなかった** | **緑**（通ったのと区別が付かない） |

  この結果、**「手元で門を全部通した」という報告が、DB 側を一度も見ていない状態でも
  成立してしまう**。PR #8 の本文にも「この門が緑であることは、DB 側を見たことに
  ならない」と書かれており、欠陥は当時から認識されていたが、門の側は直っていなかった。

  CI は無事である。`postgres` / `example-chat` の各ジョブが service container に対して
  `test:db` を直接実行しているため、**落ちれば CI は赤くなる**。
  **ずれていたのは手元の門の意味だけ**であり、それは push 前に手元の門を信じる者に効く。

- **検討した選択肢**:

  1. **`test:db` を `test` に改名して、ルートの門に混ぜる。**
     DB を持たない環境のルート門が**必ず赤くなる**。PR #3 が避けたことをやり直すだけで、
     採らない。
  2. **`test:db` 側に「`DATABASE_URL` が無ければスキップ」のガードを足す。**
     `AGENTS.md` の「擬似物へ黙ってフォールバックしない」に正面から反する。
     `test:db` を明示的に呼んだ者は DB を用意したつもりなのだから、
     未設定は**黙って飛ばす**のではなく**エラーであるべき**である。採らない。
  3. **ルートの門に、DB 段を明示的に足す（採用）。**
     `DATABASE_URL` の有無で分岐し、**どちらの場合も何をしたかを出力する。**
  4. **何もせず、文書に注意書きを足す。**
     欠陥は「読めば分かる」ことではなく「**門の出力が嘘をつく**」ことなので、
     文書では直らない。採らない。

- **決定**:

  ルートの `test` に段を1つ足す（`scripts/run-db-tests.mjs`）。
  **スクリプト名 `test:db` はそのまま**で、`test:db` 単体の意味も変えない。

  | 状態                        | 終了コード | 出力                                                   |
  | --------------------------- | ---------- | ------------------------------------------------------ |
  | `DATABASE_URL` 未設定       | 0          | **「実行していない」と、パッケージ名を挙げて明示する** |
  | 設定済み・DB テストが通った | 0          | 実行したことを明示する                                 |
  | 設定済み・DB テストが落ちた | **非 0**   | pnpm の出力そのまま + 落ちたことの明示                 |

  `test:db` を持つパッケージの一覧は**名前を直書きせず pnpm に問い合わせて作る**。
  この段の目的が「走っていないものが見えること」である以上、
  **あとから `test:db` を足したパッケージが一覧から漏れてはいけない。**

- **理由**:

  困っていたのは「DB テストが走らないこと」ではなく、
  **「走らなかったことが、走って通ったことと区別できないこと」**である。
  だから直すべきは実行範囲ではなく、**門が報告する内容**である。

  この分け方なら、PR #3 の意図（DB を持たない者の門を赤くしない）を保ったまま、
  三つの状態が三つとも別の顔になる。

- **結果（この決定が招くもの）**:

  - ルートの `test` は、`DATABASE_URL` が設定されている環境では**遅くなる**
    （DB テストを実際に走らせるため）。これは意図した対価である。
  - ルートに `vitest.config.mts` が増えた（`scripts/**` の歯だけを対象にする）。
    各パッケージは自分の `vitest.config.mts` を持つため、干渉しない
    （`packages/core` は設定を持たないが、vite は設定ファイルを上位ディレクトリへ
    遡って探さないため影響を受けない——実行して確認した）。
  - 門の歯（`scripts/__tests__/run-db-tests.test.mjs`）は、**本物の門を子プロセスとして
    起動する**。擬似の実行器に差し替えると「門が本当に DB テストを呼ぶか」を
    測れなくなるためだが、代償として歯の実行に十数秒かかる。
  - `.github/workflows/ci.yml` に `root-gate-db-stage` ジョブを追加した。
    pgvector の service container を持ち、`DATABASE_URL` を設定した状態で
    `node scripts/run-db-tests.mjs`（ルートの門の DB 段そのもの）を直接実行し、
    出力に「DB テストを実行します」と「✔ DB テストも実行し、通りました。」が
    両方出ること・「DB テストは実行していません」が出ないことを検査する。
    既存の `postgres` / `example-chat` ジョブ（`test:db` を各パッケージへ直接呼ぶ、
    DB テストそのものの合否を測るジョブ）は置き換えていない。新設したのは、
    それとは別の「ルートの門の DB 段が、DATABASE_URL 在りで実際に走って緑になるか」
    という、下の「確かめていないこと」1・2つ目を塞ぐための実測である。
    既存ジョブへ段を足すのではなく並列の別ジョブにしたのは、`postgres` job
    （直列に足すと今のボトルネックへそのまま積み増しになる）を避け、
    壁時計上の増分を既存ジョブの所要時間の範囲に収めるため
    （実測値は PR 本文を参照）。

- **これが覆るとしたら**:

  - **DB が誰の手元にも当たり前に在る状態になったとき**（例: リポジトリが
    `docker compose` などで DB を必ず立てる前提になったとき）。そのときは選択肢1
    （`test` へ混ぜる）が素直になり、この段は要らなくなる。
  - **`test:db` 以外の「環境を要求する検査」が増えたとき**（例: 本物の
    `OPENAI_API_KEY` を要求する検査）。同じ構造が二つ目・三つ目と要るなら、
    この段は「環境を要求する検査」一般を扱う形へ一般化すべきである。
    いまは1種類しか無いので、一般化しない。

- **確かめていないこと**:

  - 「永続的な自動の歯が無い」こと自体は、上記「結果」に書いた `root-gate-db-stage`
    ジョブで塞いだ——push・PR のたびに走り、順方向（`DATABASE_URL` 在り・対象
    パッケージが全部通ったときにこの段が緑になること）を測る。ただし歯（vitest の
    unit test）ではなく**CI ジョブ**であることは区別しておく——手元で恒常的に
    再現する歯ではなく、GitHub Actions の environment でだけ走る。逆向き（DB 段が
    呼ばれなくなる・落ちても赤くならない）は引き続き
    `scripts/__tests__/run-db-tests.test.mjs` の歯が押さえている。
  - **このジョブが実際に GitHub Actions 上で緑になることは、この文書を更新した
    作業者自身は確認していない。**作業環境に push 権限も本物の Postgres も無く
    （本項目3つ目と同じ制約）、手元では `DATABASE_URL` を設定した状態での
    `node scripts/run-db-tests.mjs` の実行を検証できなかった。**push した後に、
    このジョブが実際に緑になることを確認する必要がある**（次の作業）。
  - **この段の「DB 在りで緑」を実測した DB は、本物の PostgreSQL ではなく
    PGlite（WASM 実装）である。**作業環境に docker も postgres も root 権限も
    無かったため。pgvector・HNSW・`EXPLAIN` を含め `packages/postgres` の
    90 本中 86 本が通ったが、`migrate-ledger-handover.test.ts` の 4 本は
    PGlite が `CREATE DATABASE` を実質 no-op として扱う（独立した使い捨て DB を
    作れない）ため落ちる。本物の PostgreSQL に対する CI では、この 4 本も通っている。
